# EntityType ids — the NRL type namespace

`BW::EntityType::find` (`sub_14039A7F0`) is a plain index into one global
vector of type records, and that index is what an NRL `CreateNode` message
carries as a dynamic component's type id. Entities and components share the
namespace: entities first, then the dynamic components in
`scripts/components.xml` order.

Read out of the live 2.4.1.1 client with `tools/dump_entitytypes.py` (or
the same walk through `pyconsole`, which needs no ptrace permission). The
vector's begin/end are at `0x144B5E160`/`0x144B5E168`; each element points at
a record whose first field is the `EntityType *`, and the name is a
`std::string` at `+8` with its SSO capacity at `+32`.

Getting one of these wrong is not a soft failure: the client builds whatever
type the id names, and a component whose property count or types differ from
the child list runs the NRL decoder off the end of the stream
(`MF_ASSERT_DEV FAILED: pCurr_ + nBytes <= pEnd_`). An id that names an
*entity* is safe — the client logs
`PyEntity::createDynamicComponent: <Name> failed to load` and carries on —
which is how `OwnVehicle` at 50 (`HWDeathZone`) was caught.

## How this is used

`login/nrl.go`'s `EncodeNrlAttachComponent` puts one of these ids in every
`CreateNode` message. The rules that go with it — the child list is
properties then client methods then a trailing child, and the properties are
read size-sorted rather than in declaration order — are in
`PRIVATE_SERVER.md` under "Dynamic components". `tools/gun_probe.py`
dumps the runtime state of the chain that depends on them.
